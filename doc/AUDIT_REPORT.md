### 🔴 Critical findings (detailed)

**C1. VistaTaskHead3D.block is an nn.Sequential whose child indices shift with two construction-time booleans (in_channels != refine_channels, and dropout > 0), so the persisted head key indices (block.0/1/2/4 in the checkpoint) are fragile to feature_size/head_in/dropout changes.**

- **Location:** `nanocosmos/models/vista/heads.py:101-133`
- **Issue type:** checkpoint risk  |  **Severity:** 🔴 critical  |  **Checkpoint-safe fix:** yes
- **Detail:** The head builds a list conditionally: a width-matcher Conv3d is prepended only when `self.in_channels != refine` (heads.py:102-105), and a Dropout3d is appended only when `dropout > 0` (heads.py:128), before the final Conv3d (heads.py:131). The shipped checkpoint sits in the (matcher present, dropout present) configuration: keys are `block.0` (Conv3d 96->64 width matcher, since decoder hidden_ch=96 != refine=64), `block.1`/`block.2` (UnetrBasicBlocks), index 3 = Dropout3d (dropout=0.5, no params so absent from state_dict but consumes the index), `block.4` (final Conv3d 64->32). If a future load builds the head with dropout=0 (matcher present, no dropout) the final conv becomes `block.3` instead of `block.4`, and if head_in happened to equal refine the matcher would vanish and every subsequent index shifts by one -> load failure / silent misload. The renumbering is a real, currently-active fragility (this exact checkpoint depends on both branches being taken).
- **Recommended action:** Do NOT rename or reindex anything (that would break the shipped checkpoint). Add a module-level docstring/comment in heads.py documenting the exact index map for each (matcher, dropout) combination and warning that changing feature_size / head_in / dropout between train and resume renumbers block.{N} keys. In doc/ARCHITECT.md, record that the shipped checkpoint requires feature_size=64 (head_in=96 != 64 -> matcher present) AND dropout>0 (-> final conv at block.4).

**C2. VistaTaskHead3D.block is a bare nn.Sequential whose child indices shift with (in_channels==refine_channels) and (dropout>0), so a config change to dropout/feature_size renumbers state_dict keys and breaks strict resume of last.ckpt.**

- **Location:** `nanocosmos/models/vista/heads.py:102-131`
- **Issue type:** checkpoint risk  |  **Severity:** 🔴 critical  |  **Checkpoint-safe fix:** yes
- **Detail:** The head is built as `nn.Sequential(*layers)` where the width-matcher `Conv3d(in,refine)` is prepended only when `in_channels != refine_channels` (heads.py:102) and a `nn.Dropout3d` is inserted only when `dropout>0` (heads.py:128). The actual last.ckpt (a JointPredict3DModule, variant=2B) stores `model.decoder_adapter.head.block.0` (the 96->64 width matcher), `block.1/2` (UnetrBasicBlocks), and `block.4` (the final 64->32 Conv3d) -- i.e. block.3 is the dropout slot (no params, hence the index gap) and the final conv is at index 4. That layout ONLY reproduces when BOTH `in_channels(96)!=refine(64)` AND `dropout(0.5)>0`. Because scripts/train.py:844 builds the module fresh from the live Hydra config (build_module) and then full-resume goes through `trainer.fit(ckpt_path=...)` (train.py:797) which does Lightning's default STRICT load_state_dict, resuming last.ckpt with a config whose `model.dropout=0.0` (e.g. configs/snemi3d.yaml:390, configs/default.yaml has 0.2) rebuilds the head with the final conv at `block.3` -- every subsequent key renumbers and the strict load raises a missing/unexpected-key RuntimeError. The checkpoint's own hparams record dropout=0.5, but hparams are never read back (no load_from_checkpoint / self.hparams anywhere), so nothing enforces the match. This is the single highest-probability way an operator breaks resume of the existing 12GB checkpoint.
- **Recommended action:** Do NOT change the head module structure or attribute names (that itself would break last.ckpt). Instead, pin the checkpoint-affecting model_config values (`dropout: 0.5`, `feature_size: 64`, `head_channels: 32`, `variant: 2B`, `vae_symmetrize_z: true`, `highres_skip: false`) in the resume config and document in configs/nanocosmos-2B.yaml (which is the config that produced last.ckpt) that these keys are checkpoint-structural and must not drift on resume. Optionally add a doc-only note near heads.py:100 that block indices are structural. A purely additive safety net (non-structural) would be a startup assertion in scripts/train.py that, when `training.resume_from_checkpoint` is set, compares live `model.dropout>0` and `feature_size`/`head_channels` against the ckpt's saved hyper_parameters and aborts with a clear message before the strict load.
- **Verifier note:** Two trivial line-number nits in the detail (not affecting the finding): build_module in scripts/train.py is at line 843 (finding says 844); the trainer.fit(ckpt_path=...) call is at train.py:797 but sits inside run_fit_with_recovery, while the resume decision (return str(resume_ckpt)) is at train.py:726-728 via _resolve_checkpoint (finding attributes the strict-load path to train.py:797 which is accurate for the fit call itself). The head-file location (heads.py:102-131) and all checkpoint/config evidence are exact. The recommended action (pin dropout:0.5/feature_size:64/head_channels:32/variant:2B/vae_symmetrize_z:true/highres_skip:false in the resume config, doc-only notes, and an optional additive startup assertion in scripts/train.py) does NOT alter any __init__ signature, nn.Module attribute name, or state_dict key, and explicitly warns against changing the head structure — hence checkpoint-safe.

**C3. Unified-head width (final head Conv3d out-channels, i.e. block.4 out-channels) is derived at construction from the loss offset set, not from the persisted model.head_channels, so a change to the offsets silently renumbers/reshapes the head and breaks load of the 12GB checkpoint (head_channels=32).**

- **Location:** `nanocosmos/modules/base.py:137-148`
- **Issue type:** checkpoint risk  |  **Severity:** 🔴 critical  |  **Checkpoint-safe fix:** yes
- **Detail:** BaseCircuitModule.__init__ computes `_head_channels = len(loss_offsets) + 2` and OVERRIDES model_config['head_channels'] with it (base.py:148). The real last.ckpt is a JointPredict3DModule whose head final conv `model.decoder_adapter.head.block.4.weight` has shape (32, 64, 1, 1, 1) -> head_channels=32, which comes from the joint loss's nested `loss.seg.offsets` (30 offsets, verified in hyper_parameters['loss_config']['seg']['offsets']). The default AFFINITY_OFFSETS today is only 14 (HEAD_CHANNELS=16), so any load path that does NOT restore the exact saved loss_config (or that uses the flat AffinityFGLoss `_loss_offsets` which returns None -> falls back to 14) rebuilds the head at out_channels=16 and the (32,64,...) checkpoint tensor fails to load. The head width is thus coupled to an external/config-derived count rather than a stored scalar. This is not fixable by code without changing behavior; it is a documentation/guard gap.
- **Recommended action:** Do NOT change the derivation or any names/shapes. Add documentation at base.py:137-148 (and in doc/ARCHITECT.md) explicitly stating that the persisted `model.head_channels` is informational only and the actual head width is pinned by the loss offset set at load time, and that resuming the shipped checkpoint REQUIRES loss.seg.offsets to still contain exactly 30 entries (head_channels=32). Optionally add a non-fatal assertion/warning comparing the derived head width against a checkpoint's saved head_channels when resuming, but only as an additive warning that does not alter construction.

**C4. The HuggingFace token is re-added to the same model_config dict that self.hparams references, so it is serialized into every checkpoint's hyper_parameters in plaintext -- the opposite of what the code comment claims.**

- **Location:** `nanocosmos/modules/cosmos_2_5_common/base.py:82-86`
- **Issue type:** checkpoint risk  |  **Severity:** 🔴 critical  |  **Checkpoint-safe fix:** yes
- **Detail:** Line 83 pops hf_token from model_config, line 84 calls self.save_hyperparameters(). Lightning's save_hyperparameters (pytorch_lightning/utilities/parsing.py:192,206) stores the SAME model_config dict object by reference into self._hparams; it only deep-copies into _hparams_initial. Line 86 then re-inserts hf_token into that very dict object, which is still referenced by self._hparams. At checkpoint time, dump_checkpoint (checkpoint_connector.py:495) serializes dict(obj.hparams) -- the MUTABLE _hparams, not _hparams_initial -- so hyper_parameters.model_config.hf_token is written to the .ckpt in cleartext whenever a token is configured. I verified the repo's last.ckpt contains hyper_parameters.model_config with variant/head_channels/pretrained/vae_symmetrize_z; hf_token is absent there only because that run had hf_token=None (line 85 skipped the re-add). The comment at :82 ('intentionally not persisted') is therefore false for any run with a real token.
- **Recommended action:** Do not mutate the dict that self.hparams holds. Either (a) pass ignore=['model_config'] plus a token-stripped copy to save_hyperparameters, or (b) build a separate dict for _build_model rather than re-adding hf_token to the hparam-referenced one, or (c) add self.hparams.model_config.pop('hf_token', None) immediately after re-adding so the mutable hparams stay clean. This is doc/runtime-only and does not change state_dict keys or __init__ signatures. Also correct the misleading comment. Consider whether existing checkpoints on disk may already embed a token.
- **Verifier note:** Location and mechanism are accurate as stated (base.py:82-86). No correction needed. One clarifying note: the recommended action is confirmed safe. _build_model (base.py:118) reads hf_token via model_config.get('hf_token'), so options (a) ignore=['model_config']+stripped copy, (b) separate build dict, or (c) self.hparams.model_config.pop('hf_token', None) after re-add all keep the token reaching the HF loader while removing it from _hparams. None of these alter the __init__ signature (model_config/optimizer_config/loss_config/training_config), any nn.Module attribute name, or any state_dict key — hf_token is a load-time credential, never a persisted weight. The severity of 'critical' is justified: any real-token run writes the token to .ckpt hyper_parameters in cleartext.

**C5. torch.load is globally monkeypatched to force weights_only=False for the entire process, disabling the safe unpickler for every checkpoint (including untrusted ones).**

- **Location:** `scripts/train.py:154-160`
- **Issue type:** checkpoint risk  |  **Severity:** 🔴 critical  |  **Checkpoint-safe fix:** yes
- **Detail:** _install_runtime_patches() replaces the module-global torch.load with a wrapper that unconditionally sets kwargs['weights_only']=False, then assigns it to torch.load. This is not scoped to the known-good project checkpoint: every torch.load anywhere in the process (Lightning's own ckpt restore at trainer.fit(ckpt_path=...), HF weight loads, MONAI VISTA3D loader in hf_loader.py, any dependency) now runs the FULL pickle unpickler with arbitrary-code-execution semantics. Any .ckpt or .pt fed via +ckpt_path=, training.resume_from_checkpoint=, or a HF/remote download is trusted implicitly. The add_safe_globals allow-list at :147 is rendered moot by the forced weights_only=False. Torch's default flipped to weights_only=True precisely to prevent this; the patch reverts that protection globally and permanently for the run.
- **Recommended action:** Do not overwrite the global torch.load. Instead pass weights_only=False only at the two call sites that genuinely need it (the explicit warm-start torch.load at :740, which already passes it, and Lightning's restore path via a Trainer/torch context), and rely on add_safe_globals for the rest. If a blanket override must stay, gate it behind an explicit opt-in flag and document that only locally-produced checkpoints may be loaded. Keep the change confined to train.py load-time behavior; it does not touch any serialized key or __init__ signature.
- **Verifier note:** The detail wrongly lists the MONAI VISTA3D loader in hf_loader.py as an affected torch.load site; that loader uses safetensors (safe_open + hf_hub_download of model.safetensors at hf_loader.py:100), never torch.load, so it is unaffected and inherently safe. The remaining genuinely-affected paths (Lightning's trainer.fit(ckpt_path=...) restore at train.py:797, and the explicit warm-start torch.load at train.py:740) are correct. Core finding and location (train.py:154-160) are accurate.

**C6. Module is rebuilt from the live Hydra config (not from the checkpoint's saved hparams) before full-resume strict-loads last.ckpt, so any drift in structural model_config keys silently renumbers/adds/removes state_dict keys and breaks the load.**

- **Location:** `scripts/train.py:844`
- **Issue type:** checkpoint risk  |  **Severity:** 🔴 critical  |  **Checkpoint-safe fix:** yes
- **Detail:** build_module(cfg) at train.py:844 constructs the LightningModule from the current cfg.model/loss/optimizer/training dicts (train.py:365-370), and _resolve_checkpoint returns the ckpt path for `trainer.fit(ckpt_path=...)` (train.py:726-728, 797) which performs Lightning's STRICT load_state_dict. The checkpoint's saved `hyper_parameters` are never consumed (grep for load_from_checkpoint / self.hparams returns nothing in the package), so the on-disk config is the sole source of truth for structure. last.ckpt was produced by configs/nanocosmos-2B.yaml (model.type=joint3d_2b -> JointPredict3DModule, variant=2B, head_channels=32, dropout=0.5, feature_size=64, vae_symmetrize_z=true, freeze_dit_backbone=5, freeze_vae_decoder=true -- all match the ckpt's hyper_parameters exactly). Resuming with a structurally different config drifts the following key sets: `head_channels` (final head conv out-channels), `feature_size` (refine width + feature_projector + fallback_down + decoder_adapter.to_latent shapes), `variant`/`pretrained` (whole `model.dit.*` class and key set: diffusers vs _StandaloneDiT3D), `highres_skip` (presence of `model.decoder_adapter.skip_stem.*` AND head_in width), and `fp8` (Float8Linear scale-buffer keys under `model.dit.*`). Note `head_channels` is additionally re-derived from the loss offset count at base.py:139-148 and overrides the config value, so the head width is actually pinned by `loss.seg.offsets` (30 -> 32) -- another structural key that must not drift.
- **Recommended action:** Keep the build-from-config flow (changing it is not checkpoint-safe). Make the coupling explicit and enforced without touching any serialized surface: (1) document in configs/nanocosmos-2B.yaml and doc/ that model.{variant,head_channels,feature_size,dropout,highres_skip,pretrained,vae_symmetrize_z,fp8} and loss.seg.offsets are checkpoint-structural for last.ckpt and must be held fixed on resume; (2) add an additive preflight check in scripts/train.py that reads the resume ckpt's `hyper_parameters` (already present, verified) and errors out on a structural mismatch before the strict load. Both are doc/validation-only and add no state_dict keys or __init__ signature changes.
- **Verifier note:** Minor, non-load-bearing notes only: (a) fp8 is NOT set in nanocosmos-2B.yaml (it is set in nanocosmos-4B.yaml:491); it remains a valid structural-key warning since toggling it on resume adds Float8Linear scale buffers, but the concrete last.ckpt was built with fp8 off. (b) vae_symmetrize_z drift is a latent-distribution-shift caveat (wrapper_base.py:170-173 documents it as not resume-clean) rather than strictly a state_dict-key mismatch; still valid to hold fixed. (c) The finding's model-package paths omit the top-level 'nanocosmos/' prefix but resolve correctly. The recommended actions -- (1) doc-only config/doc annotations and (2) an additive preflight in scripts/train.py that reads the already-present ckpt hyper_parameters and errors on structural mismatch before the strict load -- add no state_dict keys, no nn.Module attribute renames, and no __init__ signature changes, so both are checkpoint-safe.
